網站速度常被簡化成「首頁幾秒打開」。但使用者在意的，通常是主要內容何時出現、按下按鈕後多久有反應，以及閱讀時版面會不會突然跳動。

因此，檢查網站效能時，不能只看一個總載入時間，也不能只看一次測速分數。

> **快速結論：** Core Web Vitals 是 Google 搜尋使用的頁面體驗訊號之一，但相關性與內容品質等因素仍然重要。改善速度有助於使用者體驗，不代表單靠分數就能提升排名。

## 先認識 Core Web Vitals

目前常用的三項核心指標是：

**LCP（Largest Contentful Paint）**：衡量主要內容元素出現在畫面上的時間。若首屏大圖或主要區塊載入太慢，使用者會覺得頁面遲遲沒有準備好。

**INP（Interaction to Next Paint）**：衡量使用者互動後，頁面視覺更新的反應情況。若 JavaScript 工作太多，點擊或輸入可能會延遲。

**CLS（Cumulative Layout Shift）**：衡量頁面載入期間非預期的版面位移。圖片沒有預留尺寸、廣告區塊突然出現，都可能讓內容跳動。

Google 提供的良好體驗參考門檻為：LCP 不超過 2.5 秒、INP 不超過 200 毫秒、CLS 不超過 0.1。這些數值是以第 75 百分位的使用者資料評估，不是每一次測試都必須完全相同。

## 伺服器回應時間也值得檢查

TTFB（Time to First Byte）是瀏覽器收到伺服器第一個位元組所花的時間。它不是 Core Web Vitals，但能協助判斷請求是否在伺服器或網路階段就已經延遲。

若 TTFB 偏高，可以檢查主機、快取、CDN、資料庫查詢與網路路徑。若 TTFB 正常，頁面仍然很慢，就要繼續看圖片、字體與前端程式。

不要只靠一個固定的毫秒門檻決定是否換主機。不同網站架構、地區與測試環境差異很大，應先比較多次測試與真實使用者資料。

## 常見問題與檢查方向

**1. 首屏圖片太大**

確認圖片尺寸是否符合實際顯示大小，並考慮使用 WebP 或 AVIF 等適合的格式。首屏主要圖片通常不應被不必要地延遲載入；其他非首屏圖片則可依情況延遲載入。

**2. JavaScript 工作過多**

檢查是否載入不必要的套件、第三方追蹤碼或大型互動元件。INP 不佳時，應觀察互動期間主執行緒是否被長任務占用，而不是只看 JavaScript 檔案大小。

**3. 圖片與廣告造成版面跳動**

為圖片、影片與廣告預留空間，設定適當的寬高或長寬比。這有助於降低 CLS。

**4. 字體載入影響呈現**

確認是否載入過多字重與字型檔，並評估字體子集、快取與 `font-display` 設定。中文字型檔可能很大，應特別留意載入策略。

**5. 快取與資源傳輸設定不理想**

檢查靜態資源的快取標頭、壓縮與 CDN 設定。靜態網站也可能因為圖片太大、腳本過多或快取不完整而變慢。

## 用什麼工具檢查？

- **PageSpeed Insights**：查看頁面效能測試，以及有資料時的真實使用者體驗資訊。
- **Chrome DevTools Lighthouse**：在特定測試環境中檢查頁面，適合比較修改前後的實驗室結果。
- **Chrome DevTools Performance**：追查互動延遲、長任務與資源載入問題。
- **Search Console Core Web Vitals 報告**：觀察網站中符合資料條件的網址群組表現。

實驗室測試適合定位問題，真實使用者資料則反映不同裝置、網路與使用情境。兩者應搭配閱讀，不要把一次測試結果當成所有訪客的體驗。

## 修復順序怎麼排？

先選擇有流量、對業務重要的頁面測試，再找出最明顯的瓶頸。一次優先處理一類問題，修改後用相同條件重新測試，並觀察真實使用者資料是否改善。

不要為了把分數從 90 拉到 100，犧牲實際功能或內容呈現。網站效能的目標，是讓使用者更順利地取得資訊與完成操作。
